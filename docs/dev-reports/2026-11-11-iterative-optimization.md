## 收敛条件

本次按“定位 → 改进 → 针对性检查 → 复审”的顺序循环。收敛条件是：已确认且当前环境可处理的问题有修复和回归覆盖；性能改动有原实现对比；模块接线与发布资源检查通过；最终全量检查通过；再次复审未发现所改路径中的新增阻断问题。

这不是对任意浏览器规模的最优性能保证。真实 Electron/Chromium 负载、Windows/macOS 原生窗口和 Rust 编译需要对应环境，本次继续保留这些验收边界。

## 迭代一：减少队列和大集合的重复工作

| 位置 | 发现的问题 | 实施与检查 |
| --- | --- | --- |
| `automation/task-scheduler.js` | pending 每取一项都 Array.shift，积压较大时反复搬移后续元素 | 使用队首游标、释放已消费引用、周期压实；检查 5,000 项 FIFO、耗尽后释放数组、重用与部分排空后销毁 |
| 同一调度器 | 注入的间隔 sleep 拒绝会使内部 Promise 链拒绝，即使任务本身已成功 | 统一异常观察入口并捕获间隔失败；检查观察器也抛错时后续任务仍能排空，不改变任务成功结果 |
| `renderer.js` 批量移除/恢复/回滚 | filter/includes、循环 find、filter/some 导致反复扫描整个环境列表 | 提取 `ui/ui-profile-batch.js`；每次操作创建一次 ID Set，扫描一遍列表；检查顺序、引用、不存在 ID、重复 ID 和 10,000 项线性读取次数 |
| 同步文本分配排序 | 每次比较都在会话数组 find，并重新读取显示编号及创建数字排序配置 | 提取 `ui/ui-sync-text.js`；建立会话 Map、预计算编号并复用 Intl.Collator；检查数字顺序、相同编号、缺失会话、分发游标及随机输入 |
| UI 启停工作池 | 逐项 shift 同样搬移等待数组 | 以共享游标领取任务，保留原并发数和异常传播语义 |

这轮专项通过后，复审了原有调用方向、状态引用、FIFO、销毁和错误观察策略。调度器容量上限及超时取消涉及业务策略，未在此次更改默认行为。

## 迭代二：修复缓存正确性，缩短真实集成检查等待

复审行构造函数与缓存键发现：平台 startUrl/type 副标题、createdAt、启动 message 以及回收站剩余时间没有完整参与缓存键。updatedAt 不变时，这些显示变化可能沿用旧行。

将缓存键提取到 `ui/ui-profile-rows.js` 的 `profileRenderKey()`，补全显示依赖。renderer 显式提供主题、语言、分组、编号和剩余时间文本。检查字段变化是否真正替换对应行，同时确认 Cookie 等非显示字段变化不会重建行；未变化页仍维持零移动。

MCP 自测原先对每个子进程固定等待 6 秒，即使请求早已全部返回。现在收到所有预期请求 ID 的响应即可完成，并清理计时器；6 秒仅作为失败期限。真实 HTTP/stdio 的原有 61 个检查保持通过，没有删除或跳过检查。

## 迭代三：最终复审与交付检查

逐项复核：新 UI 模块均在 renderer 使用前加载；只通过 window 命名空间导出，不增加共享词法变量；新运行模块落在既有发布清单的 ui/rpa 目录；自测与基准仍由发布过滤排除。批量状态修改保留记录对象，未改变显示排序和活跃任务保留策略。调度器销毁只拒绝等待任务，仍等待正在运行的任务结束。

最终复审没有发现上述修改路径中新的阻断问题。较大的 renderer、内核管理和同步入口仍可继续按领域拆分；真实桌面数据和跨平台验证仍是进一步性能决策的前提，不以持续搬动文件替代这些数据。
