## 1. 本次目标与范围

## 2. 逐轮发现、修复与复核

### 第一轮：设置持久化与启动队列

**设置可能漏写。** 文件写入过程中，第二次保存替换了实时缓存；旧代码完成第一次写入后，把此时的新缓存记录成“已持久化”。下一轮的去重判定因此跳过第二次写入。故障注入用例复现为：请求保存 `memoryLimit=82`，文件仍是 `81`。

修复为：在异步文件操作前捕获独立快照，写入内容与成功后的持久化标记使用同一快照。另移除替换前删除旧文件的步骤；直接原子重命名，重命名失败时旧文件仍可读取。用例覆盖并发修改、替换失败、失败后重试。

**启动队列在名额占满时进行平方级扫描。** `acquireNext()` 对每个候选任务重新遍历任务列表计算启动数量。修复为：同一次同步搜索中只计算一次启动通道占用，并保持批任务能够使用独立通道。第五轮又改为按需计算，避免只有批任务时引入多余扫描。

### 第二轮：DNS 缓存、取消与异常响应

| 发现 | 修复后的行为 |
| --- | --- |
| `TTL=0` 被替换为默认 60 秒；混合记录中的零 TTL 被忽略 | 当次返回答案但不缓存，并清除同键旧缓存 |
| 只依据最终地址 TTL，忽略较短的 CNAME TTL | 缓存期限受响应中相关记录类型及 CNAME 的最短 TTL 限制 |
| 用户取消后继续尝试其他 DoH 端点 | 使用取消代次，立即终止旧查询的端点切换 |
| 取消后立即重查仍可能合并到已取消请求 | 清理旧在途映射，旧任务完成时不删除新任务的映射 |
| 网络超时被标记成用户取消 | 超时返回 `ETIMEDOUT`，用户取消返回 `ECANCELLED` |
| 域名大小写与末尾根点造成重复请求 | 规范化缓存与在途查询键，共享等价域名的请求 |
| 缺少域名终止符或答案被截断时返回部分解析结果 | 拒绝不完整响应；带截断标志的响应不能作为完整结果使用 |
| TTL 过期自测被同步测试包装器错误调用 | 改为等待异步断言，使过期行为真正参与通过/失败判定 |

DoH 用例从原有 35 项增加为 43 项；新增的 8 项在修复前均失败，修复后 43/43 通过。代理与 DoH 集成检查另有 6/6 通过。DoH 检查已纳入聚合清单，重复的 npm 入口按仓库现有单一注册表规则移除，使用 `npm run selftest -- doh`。

### 第三轮：下载器

| 发现 | 修复 |
| --- | --- |
| 响应头到来前无法取消请求 | 将 AbortSignal 接入 HTTP 请求，覆盖连接及等待响应头阶段 |
| 已取消对象仍可开始下载，重试退避期间取消后可能再次启动 | 开始、重试和文件提交前检查取消状态；保留 `canceled` 状态 |
| 畸形重定向地址在异步回调中抛出未捕获异常 | 捕获 URL 解析错误并使下载 Promise 拒绝 |
| 206 续传不校验 `Content-Range` | 校验起点、区间、长度及总大小；不完整文件不得发布 |
| 传入嵌套 `destPath` 时未创建对应父目录 | 对实际目标目录做创建与可写检查 |
| 最终重命名失败前已经删除旧目标 | 直接原子替换，失败保留旧文件 |
| 手工流清理可能使重试与旧文件描述符关闭交错 | 使用支持背压和中止的 `pipeline()`，等待失败流清理完成 |
| 续传校验旧文件期间，响应错误可能无人处理 | 提前接管响应错误，随后交给管线处理 |

复核包含本地 HTTP 服务、真实文件读写、畸形重定向、错误续传范围、取消等待响应头、流中取消和模拟替换失败。下载器最终为 **38/38 通过**。

### 第四轮：环境删除与异常启动恢复

**停止失败仍可能删除浏览器数据。** 批量停止使用 `Promise.allSettled()`，但旧代码忽略拒绝结果，随后继续删除目录。新增用例在原实现中报“预期拒绝但未拒绝”，确认此路径可发生。

修复为：任何停止拒绝、退出未确认或生命周期记录仍存在，均阻止进入数据删除阶段。为每个待删环境设操作保护，拒绝删除期间的新启动和重复删除，且无论成功或失败都释放保护。回归验证目录标记文件、环境元数据和关联状态被保留。

**异常恢复忽略进程扫描的未知状态。** 恢复清理失败的环境时，旧代码只读取扫描结果中的 PID 数组；扫描失败返回“未知 + 空数组”，被误当作没有残留进程。新用例通过让进程检查程序不可用，确定性复现该问题。

修复为：最终扫描必须明确成功且无残留 PID，才允许释放锁和重新启动；否则保留旧运行记录及锁，返回 `BROWSER_HELPERS_EXIT_UNCONFIRMED`。原有未知扫描保留锁的检查继续执行。

### 第五轮：反向检查已修改路径

继续检查前几轮是否引入额外开销或遗漏状态。把启动数量计算改成惰性计算，批任务独立运行时不扫描启动通道；加入重试间隙取消及流中取消检查，防止取消状态被下一轮 `downloading` 覆盖。

队列最终 **27/27 通过**，下载器最终 **38/38 通过**。

### 第六轮：SQLite 差异写入缓存

**直接保存后，旧行哈希仍可能抑制后续正确保存。** 场景是加载 A、直接写入 B、再请求差异保存 A。原实现错误返回“0 条变化”，磁盘仍为 B。新增用例在修复前确定性失败。

**事务回滚没有回滚行哈希。** 垃圾箱/恢复批处理中，前一行更新成功后会更新内存哈希；后一行失败触发数据库回滚，但哈希还保留未提交状态。下一次保存可能因此错误跳过。

修复为：直接保存后失效对应哈希；保存、垃圾箱、恢复和删除事务失败后清空差异缓存，让后续保存重新核对。正常成功路径继续保持差异写入优化。新用例验证直接写入、垃圾箱/恢复中第二行故障、数据库回滚、再次保存，以及未改变行仍跳过写入。完整 SQLite 迁移与可靠性套件也重新通过。

## 3. 性能实测

测试条件：同一宿主、Node 24、5,000 个启动任务、启动并发 1、已有一个任务占满通道，再连续调用 5 次 `acquireNext()`，比较耗时中位数。

| 实现 | 中位耗时 | 算法 |
| --- | ---: | --- |
| 基线 `7b8dded` | 214.500 毫秒 | 在候选扫描内反复全量计数，最坏 O(n²) |
| 最终实现 | 0.115 毫秒 | 最多一次计数和一次查找，最坏 O(n) |

此前一组相同规模测量为 220.388 毫秒 → 0.082 毫秒。该微基准说明此饱和队列操作消除了明显的主线程阻塞；不能据此声称整应用、页面加载或浏览器启动有同等提速。
