# 第七轮：并发、退出持久化与数据库差异保存

日期：2026-11-10。发布目标：`zhu748/OpenBrowser` 的 `main` 分支。本次提交同时包含前六轮尚未提交的修复，前六轮详情见同目录 `2026-11-10-deep-review-and-optimization.md`。

## 本轮确认并修复的问题

| 问题 | 复现与修复 |
| --- | --- |
| CDP 已发送命令可能重复执行 | 固定时钟后，模拟输入命令已发送但同毫秒断线。原实现根据毫秒时间戳误判为发送前断线并重试；修复后只在实际调用 command 前发现连接失效时重连，发送后失败直接返回。既有发送前断线恢复仍通过。 |
| 强制持久化吞掉写入错误 | `DeferredQueue` 为后台重试吞掉异常，导致 `flushNow()` 和 `idle()` 也错误报告成功。增加显式调用的严格错误传播，后台定时任务保留原有重试策略。 |
| 并发重试可能覆盖前一次落盘失败 | 初次修复后的二次审查发现：只读取共享 `lastError` 仍有竞态，重试会先清空该值。新增用例复现后，改为让失败跟随对应 flush 的 Promise，诊断字段不再决定调用结果。 |
| 退出持久化失败可能跳过后续清理 | 对引擎、设置和 RPA 的写入失败分别记录，再继续同步器、自动化和快捷键清理；落盘失败时不执行可能包含过期状态的退出备份。用例同时注入异步拒绝和同步抛错。 |
| 等待队列持续创建轮询定时器 | 重叠 flush/idle 每 5ms 醒来检查状态。改用单次写入的完成 Promise，保持串行和迟到任务继续写入的语义。手动 flush 同时清除已失效的防抖定时器。 |
| SQLite 重复 ID 的最终值可能丢失 | 输入先修改 A、最后又恢复原值 A 时，旧实现先依据旧哈希筛选，丢掉最后一个值，反而把中间值写入。现在先按数据库主键保留最后一个输入，再判断差异。 |
| SQLite 已改变记录被重复哈希 | 保存前和事务成功后对同一记录各序列化并哈希一次。现在每个最终记录只计算一次，事务提交成功后复用；事务失败时不发布新哈希。 |

本轮还把此前未进入聚合清单的 coalesced-writer 自测纳入 CI，修正其对设置快照旧实现的文本断言，并让“立即 flush”用例真正立即触发写入，消除原来无意义的 10 秒等待。单测试入口统一使用 `npm run selftest -- coalesce`。

### 延迟队列

使用 100 个并发 flush 等待者加一个 idle，令正在执行的处理器等待 50ms，记录等待期间创建的 5ms 轮询定时器：

| 指标 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 50ms 内轮询定时器数量 | 913 | 0 |
| 释放处理器后所有等待者结束 | 约 2.38ms | 约 0.12ms |

定时器计数比单次耗时更能说明这里的变化：等待者共享完成通知，无需反复唤醒。耗时会受宿主调度影响。

### SQLite 差异判断

使用 100 个均有修改的记录，每个含 100,000 字节 Cookie 文本；只测差异判断、序列化与 SHA-256，不包含加密、磁盘和数据库事务。每种实现运行五次，取中位数。

| 指标 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 哈希次数 | 200 | 100 |
| 判断与哈希耗时 | 38.08ms | 17.51ms |

这是该 CPU 路径的测量，不代表整应用或真实磁盘写入有同等比例提速。

## 保持明确的验证边界

本机仍未完成真实 Electron/Chromium 渲染端到端检查、依赖 `/proc` 进程命令行检查的完整 Rust parity，以及 Windows/macOS 原生操作验证。前六轮记录中的 Rust 107 项测试、直接 rustfmt 和 Clippy 检查仍有效，本轮没有改动 Rust 源码。

本轮覆盖的是已经确认的并发、持久化和性能问题，不能据此认定项目不存在其他缺陷。发布使用普通前进推送，先检查远端是否有新提交；认证数据不加入源码、提交说明或远程 URL。
