# 项目复审、性能优化与代码分类

日期：2026-11-10。审查基线：`65ddc511c316e097e0f33f0bbfb283bf89903e5f`。

## 结论与范围

项目已经具备引擎领域模块、持久化合并写入、SQLite 差异保存、代理连接复用和自测注册表。继续优化的收益主要在跨模块的重复工作、异步刷新生命周期和大模块边界，而不是压缩源码或替换全部技术栈。

本次梳理桌面宿主、UI、环境引擎、持久化、代理/CDP、RPA、指纹注入、Rust 接线、构建和自测入口。重点逐段检查并修改环境同步、启动状态合并、事件刷新、SQLite 保存和商店响应读取。其他区域结合源码入口、现有文档和聚合测试检查；这不是对约 19.7 万行代码逐行完成的安全审计。

本轮修复 6 类已确认问题，提取 4 个职责明确的模块，新增 6 个聚合回归脚本和一个可重复基准工具。全部修改保存在当前工作区。

## 已修复的问题

| 级别 | 位置与触发条件 | 原行为与影响 | 本次处理 |
| --- | --- | --- | --- |
| P1 | `engine/profile-store-api.js`，调用者修改并再次提交同一个对象 | 引用缓存误判“未修改”，顶层名称和嵌套偏好修改丢失；IPC 又会复制对象，因此该缓存不适合主要调用路径 | 移除原始对象引用缓存，每次按当前内容校验 |
| P1 | `renderer.js`，状态事件间隔短于 `profileStatus()` 返回时间 | 定时器在请求发出时被清空，后续事件可启动第二个请求；慢的旧响应可能后返回并覆盖新状态 | 独立刷新调度器，同一事件通道串行执行；请求期间保留一次后续刷新，隐藏窗口暂停并在恢复时继续 |
| P1 | `chrome-store-metadata.js`，收到响应头后正文停滞 | 页面和图标的超时已被清除，正文读取继续等待；图标和 HTML 曾在完整缓冲后才检查尺寸 | 超时覆盖完整正文，流读取时限制字节并在超限时取消；HTML 4 MiB、图标 2 MiB、CRX 120 MiB |
| P2 | `engine/profile-store-api.js`，一次或连续多次环境同步 | 先直接调用 SQLite 差异保存，再经统一持久化再次检查相同记录；Cookie 较大时重复序列化和哈希 | 同步仅走统一 `persist()`；连续调用由现有写入器合并，调用者仍等待落盘结果 |
| P2 | `automation/profile-store-sqlite.js`，重复保存相同扩展及元数据 | Profile 和分配已有差异判断，但扩展及 4 个元数据键仍重复 UPDATE | UPSERT 仅在序列化内容不同的情况下更新，无需增加可变内存缓存 |
| P2 | `renderer.js`，从引擎恢复大量 UI 中不存在的环境 | 对每条记录扫描不断增长的结果数组，ID 比较呈二次增长 | 按 ID 建 Map/Set，恢复路径改为线性查找，保留原顺序与去重规则 |

前三种修复均有对应的确定性回归检查。环境同步、SQLite 重复行更新及商店正文超时检查曾在修复前执行并确认失败。引用缓存问题另外用同一对象先提交 `Before`、原地修改为 `After` 再提交的最小复现确认：修复前引擎仍返回 `Before`。

## 代码分类与精简

完整分类入口见 [代码分类与维护入口](../code-organization.md)。本轮落地的边界如下：

| 模块 | 职责 | 依赖方式 |
| --- | --- | --- |
| `Browserapp/main/kernel-ipc.js` | 内核 IPC 的 14 个频道，参数转换、分支与文件选择 | 注入 `registerTrustedIpc`、引擎、对话框；可信发送方检查继续在宿主入口执行 |
| `Browserapp/ui/ui-profile-state.js` | UI 与引擎环境的启动合并、凭据及代理恢复 | 无 DOM，通过参数注入校验及代理规则；浏览器/CommonJS 双入口 |
| `Browserapp/ui/ui-refresh-scheduler.js` | 事件合并、串行执行、迟到刷新、暂停/恢复、销毁 | 无 DOM，定时器和刷新回调可注入；浏览器/CommonJS 双入口 |
| `Browserapp/automation/response-body.js` | 有字节限制的响应正文读取与取消 | 页面、图标、CRX 共用；没有 Electron 依赖 |

`renderer.js` 通过两个命名空间使用新增 UI 模块；HTML 加载顺序和共享脚本作用域由现有加载自测覆盖。没有为新模块增加共享顶层函数名。

| 既有文件 | 修改前 | 修改后 | 变化原因 |
| --- | ---: | ---: | --- |
| `renderer.js` | 4,921 行 | 4,886 行 | 提取状态合并和刷新调度 |
| `main.js` | 1,729 行 | 1,689 行 | 提取内核 IPC |
| `engine/profile-store-api.js` | 372 行 | 344 行 | 去除引用缓存、重复保存和配套清理 |
| `chrome-store-metadata.js` | 336 行 | 309 行 | 复用正文读取，完整覆盖超时与字节限制 |

这四个文件合计减少 130 行。总仓库行数包含新增模块、测试与文档，不能把入口缩短当作总量削减，也不能把行数减少直接等同于性能提升。

运行时代码、测试、审计脚本、生成数据与第三方内核已经在分类文档中分开列出。基线仍有 44 个顶层 `*-selftest.js`，另有 13 个非自测审计脚本；后续迁移应同时更新 npm、注册表、CI、文档和相对路径。新回归脚本集中放在现有 `automation/selftests/`，性能工具放在 `scripts/`。

## 可重复性能测量

在 `Browserapp/` 执行：

```bash
TMPDIR=/可写临时目录 node scripts/benchmark-maintenance.js 65ddc51
```

基准直接从 Git 读取基线实现。环境：Linux 容器、Node v24.22.1。CPU 路径预热 2 组，取后续 9 组中位数；恢复路径每组 30 次调用。输入全部为合成数据。原始结果见 [benchmark JSON](2026-11-10-maintenance-benchmark.json)。

| 场景 | 优化前 | 优化后 | 可解释的变化 |
| --- | ---: | ---: | --- |
| 恢复 1,000 个引擎独有环境 | 2.2685 ms/次 | 0.0969 ms/次 | 读取 ID 由 999,000 次降至 3,000 次 |
| 同步 1,000 个环境，每个含 10,000 字节 Cookie 文本 | 99.4493 ms/次 | 51.3767 ms/次 | 哈希由 2,000 次降至 1,000 次 |
| 保存未变化的 100 个扩展和 4 个元数据键 | 104 次 SQLite 行更新 | 0 次行更新 | SQL 条件跳过重复值 |
| 同一数据集仅改动 1 个扩展 | 104 次 SQLite 行更新 | 1 次行更新 | 仅更新变化行 |

恢复基准检查输出一致，SQLite 基准检查最终扩展列表一致。同步 CPU 测量使用真实校验与哈希方法、替身存储，不包含真实加密、磁盘和 50ms 合并等待；每次输入都重新复制，模拟 IPC 传入新对象。SQLite 行计数使用真实 WAL 数据库的 `total_changes()`，并不等同于物理磁盘写入次数。

这些结果说明局部工作量下降，不能推算真实启动、UI 帧率、整应用内存或浏览器吞吐有相同倍率提升。同步仍有全量校验和一次哈希扫描，扩展仍会序列化并执行 SQL；它们尚未成为按单条补丁更新的接口。
