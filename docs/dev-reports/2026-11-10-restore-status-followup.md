# 后续优化：恢复协调与运行状态刷新

基线：`c8c4102`。本轮接续云同步/代理统计优化，完成恢复文件的进程内协调和失败回滚、恢复语义对齐，以及运行状态增量和渲染端控制器的整理。

## 已落地的行为

| 问题 | 现在的行为 |
| --- | --- |
| 写文件前检查后，浏览器仍能并发启动 | 第一次异步 I/O 前同步占用整批涉及浏览器文件的环境。启动、删除、移入回收站、清缓存、外部 Profile 同步/编辑和切换数据根目录共用该占用检查。内部恢复提交使用持有者令牌。 |
| 后一个文件无效或提交中途失败，前面的文件已被改写 | cloud/file-restore.js 在写入任何活跃文件前验证整批路径、文件数量和字节上限，并暂存新文件。提交时保留原文件，失败按逆序回滚；新创建文件会被移除。 |
| 代理、设置或引擎保存失败，浏览器文件已经替换 | 失败触发文件回滚，并标注失败阶段。回滚也失败时保留原文件备份、路径清单及环境占用，阻止进程内再次启动受影响环境；错误包含 recoveryDirectories。 |
| “完全覆盖”的界面文案与引擎实际保留本地数据不一致 | 文案明确为“云端优先（保留本地独有环境）”。旧 overwrite/remote-wins 参数兼容；同 ID 选远端，本地独有环境、分组及代理保留。没有添加删除本地独有数据的流程。 |
| renderer 的脱敏/过期快照被当作恢复源 | 环境数据以当前引擎记录为准。只提交选中的远端记录，返回保存后的真实引擎列表；恢复等待期间其他本地环境的新编辑不会被旧快照重写。 |
| 备份里明确清空凭据，UI 同步补全逻辑却恢复旧值 | 被选中的远端记录使用明确的凭据替换/代理认证清除语义。 |
| 后端已完成恢复，UI 再次后台同步全量记录 | 移除第二次 syncProfiles；UI 使用后端返回结果，避免重复持久化和后台竞态。 |
| 运行状态变了，但配置 rev 没变，增量返回空 | 独立 statusRev 跟踪启动/停止、端口、网络和扩展变化。配置 rev 继续控制编辑冲突，运行变化不会制造无效的编辑冲突。 |
| 独立保存水位与真实内存行不一致、刷新与编辑竞争 | 新 UI 控制器从实际行生成水位，直接/调度刷新共享在途请求；等待期间行数组被替换时丢弃旧响应。 |
| full 响应后再次请求完整列表、追加行反复全表查找 | full 响应直接复用 rows；增量用 Map/Set 线性合并；无变化保留数组引用。 |

## 分类边界

- `engine/profile-maintenance.js`：环境维护占用和持有者校验，无文件写入。
- `automation/cloud/file-restore.js`：路径/大小验证、暂存、提交、回滚、清理与恢复映射清单。
- `engine/status-api.js`：状态脱敏、缓存、运行版本与增量响应，保留 BrowserEngine 原公开入口。
- `ui/ui-status-controller.js`：无 DOM 的状态传输控制器，通过明确回调接收 IPC 与内存行。
- `engine/profile-revisions.js`：增加 Map 内容版本用于缓存失效；编辑版本的单调性和相同内容不增版本规则保持一致。

本轮没有添加生产依赖。语言文案修改了 JSON 源并重新生成浏览器数据桥，Node 与浏览器使用相同翻译源。

## 仍然明确的边界

- 文件回滚不把代理库、设置及引擎数据库变成共同事务。后两个存储阶段失败时，前面成功保存的元数据可能已经生效；调用方会得到错误，不能假定所有元数据均未变。
- 占用是进程内机制，文件暂存不是跨文件崩溃原子提交。进程崩溃或其他进程修改目录时，需要结合暂存目录和 manifest.json 恢复；本轮没有实现跨重启自动恢复。回滚失败时应先保留错误中列出的目录并处理原文件，再恢复使用。
- UI 其他大型功能仍有共享全局状态。大包的 JSON/AES 主线程处理、同步器和内核管理器的进一步拆分留待独立改动，避免将数据恢复与整套运行架构同时重写。
- 本轮修改在纯 Node 环境验证；未运行真实 Electron/Chromium 或 Windows/macOS 原生桌面验证，未修改或构建 Rust 核心。
