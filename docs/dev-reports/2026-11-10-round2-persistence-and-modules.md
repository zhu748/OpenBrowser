## 两个复现问题

### 退出刷新错误地报告成功

原实现将写入 Promise 接到 `.then(resolve, reject)`，返回的是调用拒绝回调后产生的已成功 Promise。普通保存请求确实被拒绝，但退出流程等待的 flush 已成功，从而无法据此阻止后续备份。

现在请求和退出排空都使用合并写入器的严格错误路径；退出排空还会等待写入期间新增的请求。底层串行写入队列保留可继续重试的分支，显式刷新另行等待真实写入结果。

### 数据库删除失败后丢失内存分配

原扩展删除顺序是删除内存记录和 Set 分配，再执行 SQLite 删除。注入数据库异常后，扩展及关联在内存中均已消失。现在先完成数据库事务，再修改内存与缓存；事务失败时保持调用前的状态。

## SQLite 实测

命令：在 `Browserapp/` 运行 `node scripts/benchmark-persistence.js`。Node v24.22.1，1,000 个环境，每个初始分配 3 个扩展；使用两个实际 SQLite WAL 文件对比原逐环境 `setAssignments()` 和新差异入口。每种场景预热两次，再取 9 次中位数。

| 场景 | 原耗时 | 新耗时 | 事务数，原→新 | 实际行变更，原→新 |
| --- | ---: | ---: | ---: | ---: |
| 分配全部未变 | 25.8252 ms | 0.3320 ms | 1,000→0 | 6,000→0 |
| 仅一个环境改变 | 25.2963 ms | 0.4726 ms | 1,000→1 | 6,002→8 |

原始结果见 [基准 JSON](2026-11-10-round2-persistence-benchmark.json)。每个改变的环境按完整 Set 替换关系，因此单个关系变化仍可能删除并重建该环境的多条关系；本轮没有承诺逐关系的最少写入。

这些结果只覆盖扩展分配的保存路径，不包含 Profile 加密、浏览器、UI、完整引擎保存和备份。缓存预热、磁盘和宿主负载均会影响耗时，事务数及实际行变更更适合复核优化是否生效。
