| 批量同步后半段输入无效，前面记录已经被修改 | 提取 `prepareProfileSync()`，先暂存全部校验、合并、扩展继承和失效记录，再一起发布 | 无效 ID 放在末尾时，现有 Profile、分配 Set 和网络状态均不变；修复前失败；重复 ID 仍按顺序合并 |

会话查询的名额由底层 I/O 完成后释放。本轮没有用 `Promise.race` 提前返回超时结果并让底层连接继续运行，因而并发上限对应实际尚未结束的查询。

## 事务与恢复契约

`ProfileStoreSqlite.withTransaction()` 统一了 11 处事务模板。最外层执行 BEGIN/COMMIT，嵌套调用使用 SAVEPOINT/RELEASE；内层失败可以回滚到保存点，外层失败则撤销整个引擎保存。

任何回滚均清空 Profile 哈希和分配快照。这样，内层保存曾发布到内存的临时差异结果不会在外层回滚后使下一次重试误判“已落盘”。数据库连接关闭也会清理哈希缓存。检查还注入了 COMMIT 前失败，确认事务层级复位、数据回滚并可重试。

事务回调必须同步。引擎状态保存不包含单独维护的分组表、设置文件、RPA 文件，也不包含磁盘环境目录操作；这些资源没有共同事务。输入校验失败不会发布内存修改；数据库保存失败时保留内存待重试状态，错误继续向调用者传播。

## 可重复测量

在 `Browserapp/` 使用 Node 22.12 或更新版本及可写临时目录：

```bash
node scripts/benchmark-session-persistence.js 65ddc51
```

基准从 Git 提取旧实现，使用合成 Profile、真实本地 HTTP 请求以及真实 SQLite WAL 文件。原始数据见 [基准 JSON](2026-11-10-session-persistence-benchmark.json)。执行环境为 Linux、Node v24.22.1。

| 场景 | 基线 | 当前实现 |
| --- | ---: | ---: |
| 10 个运行环境、两个同时查询者：HTTP 请求总数 | 20 | 10 |
| 同上：实际 HTTP 峰值 | 20 | 8 |
| 100 个运行环境、两个同时查询者：HTTP 请求总数 | 200 | 100 |
| 同上：实际 HTTP 峰值 | 164 | 8 |
| 保存 100 个变化环境、25 个变化扩展及分配：显式外层事务 | 3 | 1 |
| 同上：嵌套保存点 | 0 | 3 |
| 100 条记录、每条 100,000 字节 Cookie：一次哈希扫描 | 83.425 ms | 32.513 ms |

哈希测量双方均对每条记录只调用一次哈希，不包含上一轮“去掉重复保存”带来的次数减少。预热 2 组后取 9 组中位数；约 2.57 倍是这条序列化与哈希 CPU 路径的测量结果。

本地 HTTP 服务器对每个响应固定延迟 20ms。100 个环境整批查询由约 100ms 增至约 412ms：并发上限引入排队，以减少峰值连接和重复工作。单环境超时时间也会影响整批等待，默认 8 个名额需要后续实机负载验证。该结果不表示整应用启动或浏览器操作更快。

数据库计时保存在 JSON 中，受磁盘、缓存和宿主负载影响，本轮以完整回滚和显式事务数量为验收依据，不据一次计时声称数据库整体稳定提速。事务数量没有计入基线元数据语句的隐式提交。基准同时断言会话输出和数据库导出状态一致。
