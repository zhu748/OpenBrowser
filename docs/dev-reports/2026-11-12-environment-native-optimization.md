## 第一轮：Rust 连接池过期容量

补齐工具链后，先得到未修改 Rust 生产代码的基线：117 个测试通过，fmt / Clippy 通过。进一步检查发现两个根因、四条可复现失败路径。

| 根因或路径 | 原行为 | 当前行为 |
| --- | --- | --- |
| 访问记录回收条件为 `len > 1024`，但插入逻辑在 `len >= 1024` 时拒绝新键 | 达到上限后永远不能触发回收；即使旧记录全部过期，新目标仍失去预热资格 | 在达到上限时先清理过期记录，再判定容量 |
| CONNECT 隧道仅在取用相同目标时检查过期 | 旧目标不再访问时，过期隧道长期占据总容量 | 在预热资格与新隧道入池之前清理过期隧道和空目标队列 |
| 总容量被过期隧道占满后的预热资格 | 新目标被拒绝 | 过期容量回收后允许预热 |
| 原始 TCP 池入池前不回收过期项 | 池中旧连接已不可复用，但仍拒绝新连接 | 入池前回收过期项，保留有效容量上限 |

新增 4 项针对行为的 Rust 回归，使用真实回环 TCP 连接，并只调整私有时间戳模拟过期，避免等待 TTL 或依赖调度时延。修改前四项均失败；修改后四项通过。完整 Rust 测试增至 121 项，0 失败；fmt 和 `clippy --all-targets -- -D warnings` 再次通过。

重新构建 release 二进制，确认应用版本、协议版本与 capability 契约。针对该新二进制运行 JS↔Rust parity 8/8、chaos 5/5、打包 3/3，均通过。故障检查包含 15 次启停、实际进程与监听端口退出、传输中 SIGKILL、无响应上游，以及 50 路并发精确 payload 回显。

另运行仓库既有连接复用基准：20 ms 人工上游延迟下，冷连接 21.76 ms，预热连接 0.41 ms。该数字证明现有预热能力实际可工作；它不是本轮修改带来的新提速倍数。本轮修复解决的是 TTL 过期后该能力被容量占用阻断的问题。

## 第二轮：原生启动失败的资源清理

`native-gate-harness.js` 原先在浏览器就绪和指纹初始化之后才建立 `close()`。因此启动参数错误、spawn 失败、浏览器提前退出、CDP 就绪超时或初始化抛错时，调用方拿不到清理函数，临时 Profile 和进程可能遗留。补环境时实际观察到的 Chromium 启动失败暴露了这条路径。

现在在启动前建立共享、幂等的清理函数，整个参数构建、进程启动、就绪等待和指纹初始化都处于失败清理范围。清理会释放已建立的指纹连接，结束仍存活的浏览器，并删除临时目录。spawn 没有产生真实 PID 时不等待无意义的退出事件。

新增 `native-harness-lifecycle-selftest.js` 并注册到 SUITE，7/7 通过，覆盖上述失败、重复 close，以及不注入脚本的原生基线模式。测试使用真实临时目录，直接确认文件被移除；进程由可控适配器模拟，因此不把这 7 项描述为浏览器实际进程压力测试。其余真实原生门禁继续使用修改后的同一启动器。

## 第三轮：性能测量口径与诊断

| 位置 | 发现的问题 | 修正 |

## 第四轮：真实 WebRTC 检查与原生对照

运行新解锁的 Chromium 原生门禁时，权限/泄漏检查首次失败：等待五秒后仍处于 ICE gathering，没有收到终止事件。没有修改生产 WebRTC 逻辑或伪造事件来消除失败。

随后分别运行原生、不含 WebRTC 重写的脚本、完整脚本、仅 fallback 四组对照。未注入脚本的原生浏览器也出现了 15 秒仍在 gathering 的情况；另一些独立启动又能很快完成。这说明不同浏览器进程的冷启动时序不能直接用于判定注入回归。

门禁现改为先在同一个浏览器进程运行未注入的原生基线，再安装真实引擎指纹交付流程，运行相同探测。ICE 等待保持有界，记录状态和耗时；成功或失败都会清理定时器与 PeerConnection。

- 注入后的真实事件可观察时，仍严格检查 `isTrusted`、原生 target、候选地址、SDP 和 getStats。
- 如果原生完成而注入后超时，仍判失败。
- 只有同一进程的原生和注入后都超时且没有候选时，才明确输出 SKIP，对生命周期部分记为 partial；其余断言继续执行，不计为完整通过。

独立复核中，原生基线等待后，注入阶段实际收到原生终止事件，耗时 127 ms，权限、媒体、事件对象、SDP 和 getStats 检查通过。此前的失败和原生对照摘要保留在验证 JSON 中，不作为已确认的产品 WebRTC 缺陷。
