## 第六轮：代理持久化、退出排空与句柄释放

| 已复现的问题 | 影响 | 修改 |
| --- | --- | --- |
| `markCheck()` 等待 setImmediate 入队时调用 `flush()` | flush 返回，但本轮检查结果仍未进入持久化队列，退出时可能丢失 | flush 主动提交待办检查，并等待当前和随后到达的队列工作 |
| 检查结果在一次写入期间继续到达 | 一次等待不能覆盖新的待办 | 按当前队列身份复核，持续排空至没有新增待办 |
| `_mutationQueue` 为保持重试能力而吞掉拒绝 | 退出流程无法感知最后一次写入失败 | 保留严格的最近操作 Promise，flush 传播错误；后续操作继续使用可恢复队列 |
| 空字符串代理 ID 的错误结果只做真假判断 | 缺失记录被错误地当作成功 | 按是否存在 `missing` 字段判断，每个调用独立结算 |
| 代理库和 RPA 存储的目录 fsync 抛错 | 已打开的目录文件句柄没有关闭 | 使用 finally 确保关闭，保留平台不支持目录 fsync 时的兼容行为 |

新增 `persistence-boundaries-selftest.js`，最初六项检查全部失败；修复后通过。该脚本还覆盖了第七轮补充的 RPA 退出排空用例，最终共七项边界检查。

同时改进代理检查的批量路径：原本每个结果都用 `draft.items.find()` 扫描代理库；现在每批建立一次 ID Map，使查找由 O(N×M) 降至 O(N+M)。保留旧数据中重复 ID 的首次匹配行为、结果顺序、逐条错误及原有原子提交语义。

## 第七轮：设置读写竞争与退出时的最终保存

原先 `cloud:get-config` 和 `cloud:set-config` 每次调用都会重新读取、解密设置文件。读取期间可能已有 UI 更新正在等待 40ms 合并写入，从而用磁盘旧值覆盖新编辑。

回归直接复现：先保存内存限制 79，再请求保存 80，并立即重读，结果错误地恢复为 79。设置写入成功后，80 也没有保留下来。

修复措施：

- 云配置 IPC 使用启动时已加载的当前设置。注册这些 IPC 前，主流程已经等待设置初始化完成。
- 显式重读在开始前排空已有保存请求；读取结果通过设置修订号判断是否仍然有效。读取期间产生的新编辑优先保留。
- 并发重读共享一次进行中的读盘和解密操作，完成后释放引用。
- 明文迁移也走统一合并写入器，避免与用户保存争用固定临时文件。
- 设置写入器在有请求等待时保持 CLI 进程存活，完成后释放保活计时器。
- 设置和 RPA 的退出 flush 在首次写入后继续等待 idle，覆盖写入期间新到达的修改。

设置回归覆盖等待保存时重读、读取过程中编辑、20 个并发读取、退出写入过程中编辑、原子替换失败与重试。RPA 回归在文件 rename 期间追加新保存，确认 flush 返回前该内容已经进入最终文件。

## 第八轮：API 密钥轮换、读取和回滚

原实现的多次轮换共享可变的 `this.apiKey`。异步 mkdir/write/rename 交错执行时，各次轮换可能写入或返回别的请求生成的密钥。第一次失败的回滚也可能覆盖第二次成功的状态。

新增回归在修改前复现了三项错误：

1. 六次并发轮换仅返回一个不同的密钥。
2. 失败写入与后续成功轮换交错，破坏按请求顺序结算的预期。
3. 指定显式密钥时，先前正在读取的持久化密钥随后覆盖了它。

修复后，存储读取、显式密钥和轮换通过同一实例内的队列按请求顺序执行。每次保存捕获明确的密钥值，每次轮换返回自己的提交结果；失败只回滚该次操作，队列仍可继续工作。并发普通读取继续共享一个请求。

JSON 与可选文本临时文件在成功或失败后都清理。保留原有加密格式、显式密钥不写磁盘、旧明文迁移和不可写目录下使用会话密钥的行为。

验证包括新的四项并发检查、原有 API Key 17 项检查及凭据加密/迁移 59 项检查。

## 第九轮：最终复核发现的设置恢复边界

### 旧保存标记导致修改被跳过

如果之前保存过 A，外部文件被改成 B，再重读 B，旧的“已经保存 A”标记仍然存在。用户再次保存 A 时会被误判为无变化，磁盘却仍然是 B。

回归复现了内存限制 84 → 外部文件 85 → 重读 → 保存 84 后磁盘仍为 85。现在成功重读会更新保存快照，缺失/损坏文件与迁移会使旧标记失效，后续保存依据实际读取的状态判断。

### 损坏文件隔离与新写入竞争

只检查设置修订号还不足够：隔离损坏文件的 rename 本身会异步等待，期间新设置可能完成写入；之后的 rename 可能把刚写好的有效文件移走。

现在隔离与文件写入共用一个串行 I/O 队列；隔离开始前再次检查修订号，结束后再决定是否重置内存。新写入等待隔离结束，再替换主文件。新增受控 rename 回归确认新编辑既留在内存，也留在最终文件中。

## 验收中修复的 MCP 测试隔离问题

最后的聚合检查曾出现一项 MCP 初始化失败：读到了此前测试遗留的代理库密文，而当前密钥不能解密。原测试使用进程 ID 拼接固定文件名，并调用不存在的可选 `deleteFile` 方法，实际没有删除代理库及备份。在进程 ID 复用、临时目录保留或密钥变化时，复跑会受到旧状态影响。

测试现在每次创建独立临时目录和主密钥，结束时先停止 RPA/API，再排空代理/RPA 存储，最终在 finally 中恢复密钥环境并删除整个目录。初始化失败同样执行清理。修改后独立连续运行两次，均通过 61 项检查；随后再执行完整聚合。
